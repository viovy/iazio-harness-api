## 1. Adversarial Scope & Threat Modeling

This review interrogates the multi-slot concurrency and attribution model introduced by STORY-GOV-5274. In multi-slot fleet topologies (e.g. host `debian` housing `/home/romeo/work/meta-repo`, `/home/romeo/work/meta-repo-02`, and additional dynamic worktrees), agent processes, dispatch leases, and control-plane catalogs interact concurrently.

We model four specific failure and attack classes:
1. **Slot Hijacking & Substring Overreach**: Can an explicit slot path (`/work/meta-repo-02`) be matched or overridden by a shorter sibling prefix (`/work/meta-repo`) during binding, process detection, or HTTP projection?
2. **Deadlock / Starvation on Interrupted Story Resumption**: Does an in-flight branch worktree paused with `ReasonDirty` prevent autonomous resumption, or conversely, does clearing `QueuePaused` improperly open a worktree that was administratively halted by an operator?
3. **Split-Brain Attribution & Zombie Sibling Locks**: If a job moves between slots or completes, can a sibling slot continue reporting `LockRunning` or block other dispatches from claiming the sibling?
4. **CRAFT Honesty & Mock Evasion**: Are any tests mocking away the multi-slot interaction or skipping critical assertions?

## 2. In-Depth Adversarial Analysis

### 2.1 Threat 1: Path Suffix / Prefix Substring Overreach

#### Analysis of `iazio-agent/internal/supervisor/execution_detector.go`
- **Prior Flaw**: `strings.Contains(commandLine, cleanRP)` matched `/home/romeo/work/meta-repo` as a substring of `/home/romeo/work/meta-repo-02`.
- **Adversarial Vector**: If command line is `/usr/local/bin/iazio-harness run --worktree /home/romeo/work/meta-repo-02`:
  - `matchCommandLineRepoPath` sorts candidates descending by path length:
    1. `/home/romeo/work/meta-repo-02` (len 30)
    2. `/home/romeo/work/meta-repo` (len 27)
  - The first candidate checked is `/home/romeo/work/meta-repo-02`. Its start delimiter is ` ` and end delimiter is end-of-string. Both satisfy `isCommandPathStartBoundary` and `isCommandPathEndBoundary`. It matches and returns immediately.
  - If a command line refers only to `/home/romeo/work/meta-repo`, `/home/romeo/work/meta-repo-02` is checked first and fails (`strings.Index` returns -1). Next, `/home/romeo/work/meta-repo` is checked and succeeds.
  - If command line is `--worktree=/home/romeo/work/meta-repo-02/foo`:
    - `/home/romeo/work/meta-repo-02` matches boundary `/` at end, correctly attributing the command to slot 2.
    - `/home/romeo/work/meta-repo` followed by `-02` fails `isCommandPathEndBoundary('-')`.
- **Verdict**: Bypass vectors closed. Longest-path sorting combined with strict boundary sets prevents prefix false matching.

#### Analysis of `iazio-harness-api/internal/control/engine.go`
- **Prior Flaw**: `repoMatchesTargetOrSlotFamily` used `strings.Contains(r.WorktreePath, cleanReq)`.
- **Remediation**:
  - `repoExactPathOrAliasMatch` strictly compares `cleanWT == cleanTarget`, `filepath.Clean(cleanWT) == filepath.Clean(cleanTarget)`, or normalized slot paths.
  - Basename suffix matching `strings.HasSuffix(cleanWT, "/"+cleanTarget)` is only allowed when `!strings.Contains(cleanTarget, "/")`. Thus, `cleanTarget = "/home/romeo/work/meta-repo-02"` never executes suffix matching.
  - In `findExplicitHostRepoSlot`:
    ```go
    family := dispatch.NormalizeToSuperprojectSlotFamily(cleanTarget)
    isNumberedSlotAlias := !strings.Contains(cleanTarget, "/") && family != "" && !strings.EqualFold(cleanTarget, family)
    ```
    If `cleanTarget` is `"meta-repo-02"`, `isNumberedSlotAlias` is true, resolving slot 2. If `cleanTarget` is `"meta-repo"`, it returns `nil`, preventing a generic request from pinning an explicit numbered slot.
- **Verdict**: Sibling slot isolation is cryptographically and path-semantically sound.

### 2.2 Threat 2: Starvation via Dirty Pause vs. Unintended Unpause

#### Analysis of `BindDispatchJobRepo` & `HeartbeatWithCapabilities`
- **Prior Flaw**: Resuming an interrupted story on a dirty worktree failed because `BindDispatchJobRepo` filtered candidate slots with `isRepoSlotIdleForDispatch(r)`, which rejected `QueuePaused`. Step 3 then fell through to bind the idle sibling slot (`meta-repo`), corrupting attribution.
- **Adversarial Vector**: If a worktree was paused by an operator using `ReasonUserPaused` or `ReasonOperatorHalt`, does `BindDispatchJobRepo` accidentally unpause it?
- **Inspection of Code (`engine.go:2209-2212`, `catalog.go:379-382`, `server.go:3753-3756`)**:
  ```go
  if explicitSlot.Queue == QueuePaused && (explicitSlot.Reason == ReasonDirty || explicitSlot.Reason == ReasonAdhocASE || explicitSlot.Reason == ReasonDetached) {
      explicitSlot.Queue = QueueOpen
      explicitSlot.Reason = ""
  }
  ```
  - Pause clearance is guarded strictly by reason: ONLY `ReasonDirty`, `ReasonAdhocASE`, or `ReasonDetached` are cleared.
  - If `explicitSlot.Reason` is `ReasonUserPaused`, `ReasonQuarantine`, or any other administrative state, `explicitSlot.Queue` remains untouched.
  - Conversely, when the coordinated harness starts executing the in-flight story on that slot, the dirty/detached pause is safely cleared, allowing dispatch execution without manual human unpause.
- **Verdict**: Invariant preserved. Administrative pause cannot be bypassed; autonomous recovery for in-flight story branches is unblocked.

### 2.3 Threat 3: Split-Brain & Zombie Locks Across Hosts/Slots

#### Analysis of `catalog.go:HeartbeatWithCapabilities` & `server.go:enrichRepoWithDispatch`
- **Adversarial Vector**: Suppose job `J` was previously bound to `meta-repo`, but the runner actually executed in `meta-repo-02`. Does `meta-repo` stay locked as `RUNNING_HARNESS`?
- **Remediation Inspection**:
  1. In `HeartbeatWithCapabilities`:
     ```go
     for _, other := range e.repos {
         if other != nil && other != matchedRepo && (other.RunningJobID == cleanJobID || other.LockHolder == cleanJobID) {
             other.Lock = LockIdle
             other.RunningJobID = ""
             other.LockHolder = ""
             e.notifyRepoLocked(other)
         }
     }
     ```
     Any other repo on the engine holding `cleanJobID` is immediately evicted and reset to `LockIdle`.
  2. For external dispatch jobs not in the heartbeat `active_jobs`:
     ```go
     } else if len(activeJobs) > 0 && strings.HasPrefix(r.RunningJobID, "job_") && !e.isExternalDispatchJobActiveLocked(r, r.RunningJobID) {
         r.Lock = LockIdle
         r.RunningJobID = ""
         r.LockHolder = ""
         e.notifyRepoLocked(r)
         continue
     }
     ```
     `isExternalDispatchJobActiveLocked` checks if the host's `ActiveJobs` lists `cleanID` under another slot. If so, it returns `false`, causing the engine to evict the orphaned lock from the sibling slot immediately.
  3. In `server.go:enrichRepoWithDispatch`:
     ```go
     qJob := s.findActiveDispatchJobForRepo(*repo)
     if qJob == nil {
         if strings.HasPrefix(strings.TrimSpace(repo.RunningJobID), "job_") {
             repo.Lock = control.LockIdle
             repo.RunningJobID = ""
             repo.LockHolder = ""
         }
         return nil
     }
     ```
     Even before the next heartbeat, any HTTP read through repo detail or host detail self-heals orphaned `job_<hex>` references.
- **Verdict**: Zombie locks on sibling slots cannot persist.
