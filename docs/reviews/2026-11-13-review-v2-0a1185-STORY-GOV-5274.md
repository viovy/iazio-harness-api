# Product UX, User Flow & Interaction Review: STORY-GOV-5274 (Iteration 2)

**Story Title:** Fix Multi-Slot Duplicate Running Job Attribution and Stale Dirty Pause on Host Worktrees  
**Review Iteration:** scheme_iteration=2 (kind=fixed, profile=product_ux_review)  
**Target Submodules:** `iazio-harness-api`, `iazio-agent`, `iazio-web`, `iazio-infra`, `meta-repo`  

---

## 1. UX Problem Statement & Operator Impact

Prior to STORY-GOV-5274, operators managing multi-slot hosts (such as `debian` running multiple worktrees like `/home/romeo/work/meta-repo` and `/home/romeo/work/meta-repo-02`) encountered severe UI confusion and contradictory operational telemetry:

1. **Phantom Running Jobs on Sibling Slots**:
   - Both worktree slots simultaneously displayed `Lock: RUNNING_HARNESS` and claimed the same `Active Job: job_5caae91005a69cef`.
   - Operators inspecting `/home/romeo/work/meta-repo` were misled into believing an agent was executing code in that directory when it was completely idle.
   - Operators could not schedule new work in `/home/romeo/work/meta-repo` because the UI reported it as locked by the running job.

2. **Alarming "Contradictory" Error Banner During Active Execution**:
   - On `/home/romeo/work/meta-repo-02`, where the agent was actually running, the screen displayed a large red warning card:
     > **Worktree Uncommitted Changes**  
     > *Job scheduling is halted until modified files are committed or resolved.*
   - Immediately adjacent to this red error banner was the blue card:
     > **Harness Executing Prompt**  
     > *Executing STORY-GOV-5272...*
   - This copy-state mismatch caused acute cognitive dissonance: operators could not determine if the agent had crashed, whether the run was halted, or if manual intervention ("Resume in Place" / unpause) was required. In reality, the uncommitted changes were the intentional in-progress edits made by the active story run.

3. **Accidental Operator Disruption**:
   - Confused operators were incentivized to click "Resume in Place", pause, or cancel the job, risking duplicated prompt dispatches or race conditions against the actively running autonomous agent.

## 2. Product & UX Interaction Analysis

### 2.1 Visual Hierarchy & State Precedence (`iazio-web/lib/screens/repo_detail_screen.dart`)

- **State Precedence Rule**:
  An active, supervised execution (`repo.lock == RUNNING_HARNESS` or `job != null`) represents the primary lifecycle state of a worktree. In-progress code edits are an expected byproduct of that execution, not an error state.
- **Remediation in `_RepoDetailScreenState.build`**:
  ```dart
  else if ((repo.reason == 'HALTED_DETACHED' || repo.hasFleetDirtyState) &&
      repo.lock != HarnessLockState.runningHarness &&
      repo.lock != 'RUNNING_HARNESS' &&
      job == null)
    Card(
      color: Theme.of(context).colorScheme.errorContainer,
      ...
    )
  ```
- **UX Impact**:
  - The intrusive red halt banner is completely suppressed while the harness is actively executing.
  - The screen maintains clear visual focus on the active execution progress, showing the running story, active conversation ID, and live runtime signals.
  - **Zero Telemetry Loss**: The uncommitted files chip (`Git Status: N modified files`) remains clearly visible in the top repository chips row, keeping operators informed of file modifications without falsely claiming that scheduling is halted.

### 2.2 Post-Execution Graceful State Restoration

- When the autonomous agent finishes its run:
  - If the story cleanly commits and pushes all changes, the worktree returns to `IDLE` with a clean working tree.
  - If the story run fails, crashes, or terminates with uncommitted changes remaining, `repo.lock` returns to `IDLE` and `job` becomes `null`.
  - At that exact moment, the condition `repo.lock != runningHarness && job == null` becomes true. The red `Worktree Uncommitted Changes` card immediately reappears, properly signaling to the operator that uncommitted artifacts require attention before another job can be scheduled.

### 2.3 Multi-Slot Fleet Dashboard Consistency

- **Single Source of Truth**:
  - With `isDispatchJobBoundToOtherHostRepo` in `iazio-harness-api` and strict path-boundary scanning in `iazio-agent`, only the specific worktree slot executing the task reports `RUNNING_HARNESS`.
  - The sibling slot correctly renders `IDLE` / `Queue: OPEN`, allowing operators to dispatch concurrent work to the sibling slot without artificial lock blocking.
  - The Fleet Overview and Host Detail screens no longer display duplicate running jobs on a single host.
